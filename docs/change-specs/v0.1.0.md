# Math Arcade v0.1.0 — implementation specification

**Date:** 2026-10-01, Asia/Shanghai.  
**Status:** Consolidated owner requirements and proposed engineering contract. No implementation or deployment is asserted.  
**Owner:** William McAda.  
**Baseline:** [Project brief](../PROJECT-BRIEF.md) and [source record](../SOURCE-BASELINE.md).

## 1. Result

One teacher dashboard controls a classroom arcade. Students join from iPads, receive class or individual practice, and choose among teacher-enabled games. The same student assignment and evidence remain available across games. Math Civ delivers its own embedded mathematics and has no added gate.

## 2. Teacher workflow

1. Sign in on the teacher computer and select/create a class.
2. Set class mathematics through the shared Math Practice panel: searchable skills, supported grade range, Mixed Review or Fixed Progression, question count and existing supported help options. Preview selected skills without saving or altering learner data.
3. Enable games and open a session. Display QR and readable join code.
4. See connected students, their effective assignment, current activity and synchronization status.
5. Open a student's row to edit individual mathematics using the same panel. Save and display when it will take effect.
6. Pause/resume the session or end access from the computer.

Conspicuous labels distinguish Update class default, Assign to everyone, Customize student and Use class settings. Assign to everyone previews its scope in the panel, then applies the selected settings and clears all affected individual overrides. Ordinary class changes preserve individual overrides. Preview/cancel never changes saved settings or an active task.

Save class and individual assignments across sessions. A new session can reuse them. Starting or ending a session does not clear practice history. Provide explicit reset/deletion controls separately.

## 3. Assignment contract

Use stable student IDs, not display names as database keys. Duplicate display names must remain distinguishable. Effective practice configuration is the student's saved override when present, otherwise the class default.

Each configuration has a revision and records its catalog/generator version. Each new gate records an immutable effective configuration snapshot. The server validates skill IDs and selected modes; an empty targeted selection must not silently fall back to unrelated mathematics. Preserve hidden checked skills when searching or changing ranges. Use the approved grade ordering and per-skill preview behavior in S-03-M.

Class changes and individual changes update pending configuration immediately, but do not replace an unanswered question or reset an unfinished gate. Shared-math games apply it on the next new gate. Chrono's existing run/relay snapshot is preserved initially, with Next run shown on the dashboard. Teacher pause/end remains immediate independently of math configuration timing.

If the teacher changes practice while a mini-game is running, use the new configuration at the next admission gate. A completed gate's unused admission remains tied to its selected game and student unless the teacher ends/revokes access; configuration changes alone do not demand duplicate completed work.

Math Civ does not consume these skill selections. Its dashboard activity shows Built-in math; the student's saved practice assignment still applies when they return to a shared-practice game. Do not claim an LCM assignment changes Math Civ's authored campaign tasks.

## 4. Gate policies

| Policy | Games | Required behavior |
| --- | --- | --- |
| Round entry | Vault 7, Nightfall, Journey to the West, aerial shooter, robot side-scrolling shooter | Complete one gate before each new round; no intra-round math interruptions |
| Native gates | Chrono Circuit, Olivia | Keep established trigger locations, retries and progress rules; deliver centrally assigned practice through an adapter |
| Embedded math | Math Civ | No additional entry, death, replay or periodic gate; retain authored mathematical decisions |

The round-entry loop is Select game → Complete gate → Start round → Round ends → Complete new gate to replay. The editable field is Questions per gate, not a separate number of consecutive entry gates. An initial suggested preset of five questions is an implementation default, not an additional owner requirement; expose it before session launch.

A game manifest declares time, lives, terminal death, success and failure conditions. Document the actual imported behavior; do not equate every death with round end when the established game includes multiple lives or auto-respawns. A checkpoint retry inside the same permitted round does not reset consumed active time. Use the five-minute action default only within its stated scope; explicitly review historical exceptions such as Vault 7's existing shorter action limit.

Wrong-answer assistance, answer acceptance and progression come from the selected shared math version. Record first attempts separately from eventual completion. Do not infer mastery from a completed gate or action victory. Worked examples do not themselves count as the student answering an item.

In Arcade editions, any earlier cartridge rule that buys upgrades through extra math gates must be replaced with a documented round loadout/acquisition policy so it cannot add mid-round gates. Preserve equipment functionality. Resolve exact default equipment per game when inspecting its source; do not invent or silently remove resource dependencies.

Native gates must preserve Chrono's checkpoint credit and Olivia's established encounter/reward flow. Connecting the shared question catalog is a deliberate adapter task; the current Chrono Time/Subtraction catalog is not already the shared K–7 catalog.

## 5. Admission, identity and recovery

Proposed implementation: server-owned gate records and single-use round admissions. A client cannot award itself a completed gate or mint a new round. Validate answer submissions through the canonical mathematics evaluator and avoid returning canonical answers before allowed help/review.

Bind an admission to student, session, selected game and gate completion. Starting a round atomically consumes it. Duplicate clicks, network retries and repeated start requests return the existing round instead of creating another. One active round per student. Returning after refresh resumes the existing round when supported; it never refreshes its timer or lives. A genuinely ended/abandoned round requires a fresh gate.

If a student changes games during an unfinished entry gate, preserve the unfinished work for its original game. A different game uses its own admission; do not transfer an already consumed reward. Keep a clear Return to current activity path.

Student join uses a class session code plus a roster identity. Proposed initial identity flow: the teacher creates/imports a simple roster, students claim their row, and the dashboard resolves duplicate claims. Issue a session-scoped reconnect credential so reload returns to the same learner. No student email account is required. Identity recovery from a different device is teacher controlled; a join code alone must not expose arbitrary student history or teacher settings.

Store confirmed gate progress and grants durably. Brief connection loss shows Reconnecting, neutralizes held input and pauses interactive play. Resume only after reconciling server state. The game manifest defines whether its active timer pauses or a multiplayer round continues during a personal disconnect; disconnect never creates additional play entitlement. A disconnected participant cannot freeze the whole multiplayer room.

## 6. Teacher control

The server enforces teacher-only assignment editing, game availability and session transitions. Students can read only their effective assignment and permitted session state. Never distribute teacher credentials to student clients.

Pause freezes classroom activity and clears held controls; resume requires fresh input. End closes joining and further launches, saves supported progress and returns connected students to a closed-session screen. Clients that reconnect reconcile the ended status before resuming. Teacher-controlled game availability blocks new launches; a separate stop action handles active rounds without unexpectedly discarding them.

Classroom access windows and each game's active-play duration are different settings. A paused classroom must not accidentally add or subtract time twice. Define and test one authoritative timer policy per game.

## 7. Journey to the West multiplayer

Each participant earns admission with their own assigned mathematics. Team membership never credits another student's gate. Eligible players enter a ready room. Proposed preservation of the existing design: start when all participating players are ready, with a maximum 60-second wait beginning when the first eligible player is ready. Only students with completed gates may enter active play; outstanding students continue their math and can enter a subsequent round.

Confirm ready-room details against the actual multiplayer source/specification before implementation. Retain established in-round auto-respawn rules where present. Record server authority, reconnect and dropout behavior separately from classroom configuration synchronization. A shared dashboard connection does not establish working multiplayer combat.

## 8. Math Civ adapter

Import a pinned Math Civ — Sekigahara implementation. Add Arcade launch authorization, lifecycle notifications, teacher pause/end and save/recovery integration. Produce no external math gate or round-entry charge. Preserve campaign progress when a classroom session ends; ending classroom access is not New campaign.

Retain mathematical decisions, assistance/attempt rules, economic consequences, supplies, battles and endings. Report campaign activity separately from shared-practice attempts. Only report individual math evidence if the source exposes meaningful events and an explicit mapping is implemented; no fabricated gate completions or skill mastery.

The current standalone brief forbids a backend in its own release scope. This specification authorizes an online Arcade adapter while preserving the standalone game's identity and behavior. Do not force shared LCM/equation practice into the campaign.

## 9. Architecture and source control

Proposed implementation uses a teacher interface, student interface, one classroom backend and durable persistence. Render is the preferred hosting candidate. Select the database/runtime after source inspection and disclose recurring costs before provisioning a paid service. No lesson setting requires rebuilding the application.

Reuse the canonical `OLIVIA-MAGIC-BRACELET-QUEST/src/shared-math` implementation through a pinned dependency or reproducible build import. Record upstream commit and bundle hash. Keep canonical shared fixes synchronized with the existing hosts as required by S-03-M; avoid an independently edited Arcade copy. No Mega Man ROM or emulator is part of this integration.

Use a small per-game adapter contract: initialize, launch/resume, pause, end, snapshot, dispose, and lifecycle events. Only native-gate games request practice at their established triggers. Round-entry games use the outer admission flow. Math Civ uses no shared gate request.

Game manifests record stable ID, display name, source repository/commit/path, gate policy, supported controls, save format, version, round semantics and required assets. Adapters must not modify source games merely by changing unrelated upstream deployments. Preserve asset paths and provenance.

Logical records: teacher workspace, class, student, assignment revision, session, gate/item attempt, round/admission, game save and multiplayer room. Use stable IDs, transactional admission updates and idempotent requests. Persistence and the reconnect protocol must survive backend restarts without issuing extra rewards.

## 10. Records and deletion

Save the minimum operational records: classroom identifiers, configurations, question/attempt evidence, activity state and game saves. Keep academic attempts and game results distinct. Teacher views include first-attempt accuracy, questions completed, current activity and assignments; do not label these mastery without the shared progression rule's evidence.

Provide scoped export and U-09 deletion for individual records, class/session/campaign groups and the teacher workspace. Show affected counts, cancellation and explicit confirmation. Verify cascade deletion, reload persistence, unrelated-class isolation and starting fresh. Source assets are not student records. Configure and document retention before production; do not import MathQuest's historical 48-hour target as an unapproved Arcade policy.

## 11. Implementation checkpoints

1. Establish the canonical repository and commit this design with source references.
2. Build teacher/student session flow, persistent roster, assignments and the shared mathematics service. Verify two distinct student assignments and class-wide replacement.
3. Integrate one pinned round-entry game end to end, including replay, disconnect and teacher stop. Preserve an implementation checkpoint before extended tests.
4. Integrate remaining round-entry games and Journey multiplayer, checking source-specific round semantics and loadouts.
5. Integrate Olivia and Chrono native gates and Math Civ embedded mathematics; preserve their saves and accepted behavior.
6. Run cross-game, device, classroom-network and deployment verification; preserve the exact passing candidate.
7. Package/version/release without adding features, deploy the preserved candidate and verify the actual hosted teacher/student workflow.

Each checkpoint records included games and remaining work. Do not call a one-game pilot the completed arcade or label an untested commit a verified release.
